## 0. 本次修订重点

v0.2 不再把原型当成“方案说明页”，而是按真实用户产品来设计。产品方案中的讨论、定位、设计推理写在本文档里；原型中只呈现用户真正需要看到的信息、操作入口、状态反馈和确认机制。

本次新增和修正：

1. 页面标题回归真实产品语义，例如“工作台”“外部订阅”“扩展订阅”，不再用讨论式标题。
2. 导航重新分级：构建器不作为独立导航；模板与模板共享属于同一父级；访问与共享并入订阅详情；长期 Key 放入设置。
3. 添加外部订阅、新增扩展订阅分别放在对应页面的主按钮位置，不再放在全局顶栏。
4. 外部订阅卡片内提供“基于此创建扩展订阅”，而不是全局创建入口。
5. 多来源合并必须进入 Full Override / 完整重组模式，只合并节点，不合并源规则和源代理组，以避免冲突。
6. 节点、代理组、规则改为联动模型：节点使用稳定 ID 追踪；代理组成员只能选择已知节点、已知代理组和内置策略目标；规则目标只能选择已知代理组和内置策略目标。
7. 节点不默认清洗、不默认自动分类。节点页首先展示当前可用节点，用户主动触发清洗、编辑、新增、删除等操作。
8. 地区分组属于代理组能力：用户在代理组页主动点击“生成地区代理组”或“生成推荐代理组”。
9. 规则源导入后以“规则快照”形式插入到目标代理组/内置策略目标，不再在最终 Recipe 中长期绑定远端规则源；最终配置面向目标策略组组织规则。
10. 粘贴规则、规则去重、规则规范化等可能改变用户输入的行为，必须在保存前弹出确认，说明系统将改什么、为什么改。
11. 模板只支持 Full Override / 完整重组。Patch 是源绑定的小修小补，不进入模板共享主链路。
12. 模板需要记录 ProxyParser 新增的自定义节点，但不记录外部订阅原生节点。原生节点只能通过抽象集合、标签、地区、代理组生成逻辑参与模板。
13. 代理组、规则、节点的模板化保存以操作流 / 命令为核心，而不是保存一次最终 YAML。
14. 前端交互必须使用统一组件样式，尤其是 Select / Dialog / Tabs / Popover / Toast，不使用浏览器原生下拉样式。选项可带解释说明。

## 1. 产品定位

ProxyParser 是一个面向 Clash / Mihomo 用户的订阅配置控制台。

它帮助用户托管外部订阅，抽取节点，在 ProxyParser 内重组代理组和规则，把这些组装逻辑沉淀为可复用模板，并稳定发布为客户端可长期拉取的扩展订阅。

用户心智：

```text
我不直接把机场订阅交给客户端。
我把机场订阅交给 ProxyParser。
ProxyParser 帮我看懂它、改造它、重组它、记住我的操作。
客户端只订阅 ProxyParser 给我的稳定长期链接。
```

## 2. 导航与信息架构

### 2.1 主导航

```text
工作台
订阅
  - 外部订阅
  - 扩展订阅
规则源
模板
  - 我的模板
  - 模板共享
设置
```

### 2.2 不作为独立主导航的能力

#### 构建器

构建器不是常驻 Tab。它只在这些场景进入：

- 新增扩展订阅。
- 编辑某个扩展订阅的构建逻辑。
- 从外部订阅详情中点击“基于此创建扩展订阅”。
- 从模板应用到外部订阅。

#### 访问与共享

访问与共享属于具体扩展订阅，放在扩展订阅详情中。

它包括：短期链接、分享给指定用户、非公开链接、公开访问、拉取日志、撤销访问等。

#### 长期 Key

长期 Key 是账号级能力，放在设置里管理。

扩展订阅详情中可以复制长期订阅链接，但 Key 的重置、轮换、审计等账号级管理入口在设置里。

## 3. 顶栏与主按钮原则

### 3.1 顶栏

顶栏只做全局状态、搜索、用户入口，不放跨模块创建按钮，避免和页面内主操作重复。

### 3.2 页面主按钮

- 外部订阅页主按钮：添加外部订阅。
- 外部订阅卡片/详情主操作：基于此创建扩展订阅。
- 扩展订阅页主按钮：新增扩展订阅。
- 扩展订阅卡片/详情主操作：复制长期链接、编辑构建逻辑。
- 模板页主按钮：新建模板 / 从扩展订阅提炼。
- 规则源页主按钮：导入规则源。

## 4. 核心对象模型

### 4.1 外部订阅

外部订阅是上游原料。它保存 URL、同步状态、快照、解析后的源配置。

外部订阅内的数据是只读原料，用户不直接修改源配置。所有修改都发生在扩展订阅的构建逻辑中。

### 4.2 扩展订阅

扩展订阅是客户端真正订阅的成品。

```text
外部订阅节点 + 构建模式 + 节点操作 + 代理组操作 + 规则操作 + 配置操作 + 发布设置 = 扩展订阅
```

### 4.3 构建逻辑 / Recipe

Recipe 保存的是操作，而不是最终 YAML。

它包含：

- 来源选择。
- 构建模式。
- 节点操作。
- 代理组操作。
- 规则操作。
- 配置操作。
- 模板化分析结果。

### 4.4 原生节点与新增节点

每个节点必须有稳定 ID。

节点分两类：

1. 原生节点：来自外部订阅快照。
2. 新增节点：用户在 ProxyParser 中手动新增，例如自定义 VPS 节点。

节点名称可以变化，但 ID 不变。代理组和规则引用节点时应引用稳定 ID 或抽象集合，而不是只靠节点名称。

### 4.5 代理组

代理组成员只能来自：

- 已知节点。
- 已知代理组。
- 内置策略目标。

内置策略目标包括：

```text
DIRECT
REJECT
PASS
COMPATIBLE
```

产品中统一称为“内置策略目标”。

### 4.6 规则

规则最终面向代理组或内置策略目标组织。

规则目标只能选择：

- 已知代理组。
- 内置策略目标。

规则匹配方式由系统提供固定类型，避免用户输入无法校验的任意结构。

### 4.7 规则源

规则源是远端或本地的规则素材来源。规则源可以被导入、同步、预览和校验。

但在扩展订阅 Recipe 中，导入规则源后应保存为“规则快照插入操作”。也就是说：

```text
选择规则源 -> fetch 规则 -> 校验 -> 插入到目标代理组/内置策略目标 -> 保存为规则操作
```

最终配置中的规则仍然是 for 代理组/内置策略目标的规则集合，而不是长期依赖远端规则源对象。

保留远端规则源的来源信息用于追踪和重新导入，但模板和最终配置不应因为远端规则源变化而悄悄改变用户已经确认过的规则结果。

## 5. 构建模式

### 5.1 Patch / 保留源配置并修改

适用场景：

- 源订阅本身质量较高。
- 用户只想小改节点、组或规则。
- 用户不需要模板化或共享。

产品限制：

- 不进入模板共享主链路。
- 修改源代理组、源规则、源 rule-provider、源节点等操作会被标记为 source-bound。
- 用户需要自己控制每个节点和每条规则，不自动清洗、不自动分类。

### 5.2 Full Override / 完整重组

适用场景：

- 只消费外部订阅节点。
- 自己重建代理组、规则、配置。
- 希望沉淀模板。
- 希望未来换订阅也可直接套用。

产品能力：

- 可一键生成地区代理组。
- 可一键生成推荐代理组。
- 可清空所有代理组并按推荐逻辑重建。
- 可导入规则源并插入到目标代理组。
- 可生成模板。

### 5.3 多来源合并

如果用户选择多个外部订阅来源：

- 必须使用 Full Override / 完整重组。
- 只合并节点。
- 不合并源代理组。
- 不合并源规则。
- 不合并源 rule-provider。

原因：不同来源的代理组和规则命名、引用关系、MATCH 落点可能冲突，自动合并会产生不可预测配置。

## 6. 节点模块设计

### 6.1 页面默认状态

节点页默认展示当前所有可用节点，不主动修改节点。

默认不做：

- 不自动清洗名称。
- 不自动去 emoji。
- 不自动去倍率。
- 不自动按地区分类。
- 不自动改节点顺序。

### 6.2 节点列表字段

```text
节点 ID
显示名称
来源：原生 / 新增
协议
地区标签
服务器信息（敏感字段脱敏）
是否启用
引用次数
```

### 6.3 节点操作

用户可主动执行：

- 编辑节点详细字段。
- 新增节点。
- 删除节点。
- 禁用节点。
- 批量清洗名称。
- 批量去 emoji。
- 批量去倍率标签。
- 批量替换正则。
- 手动打地区标签。

### 6.4 节点引用联动

如果节点改名：

- 代理组显示名自动更新。
- 内部引用仍然跟随稳定 ID。
- 预览 YAML 生成时再输出最新节点名称。

如果节点被删除或禁用：

- 代理组中不应再出现它。
- 规则中若存在对该节点的引用，必须提示并移除或改写。
- 用户保存前需要看到变更确认。

## 7. 代理组模块设计

### 7.1 代理组生成入口

地区分类属于代理组功能，不属于节点功能。

Full Override 模式下，代理组页提供：

- 生成地区代理组。
- 生成推荐代理组。
- 清空并按推荐逻辑重建。

Patch 模式下，不默认生成代理组，只允许用户手动修改。

### 7.2 标准代理组命令

Recipe 中保存命令，而不是保存一次性结果。

常见命令：

```text
create-proxies-group(all enabled nodes)
create-region-groups(by region tag or region detector)
create-auto-group(url-test, all enabled nodes)
create-service-group(name=AI, memberPreset=default-proxy-choice)
create-service-group(name=Streaming, memberPreset=default-proxy-choice)
create-service-group(name=Ads, memberPreset=reject-first)
create-service-group(name=CN, memberPreset=direct-first)
```

### 7.3 标准成员配置

为了让模板可复用，代理组新增时优先使用标准成员配置。

标准成员配置：

1. 默认代理选择：Proxies、Auto、地区组、DIRECT。
2. 默认拒绝：REJECT、DIRECT、Proxies。
3. 默认直连：DIRECT、Proxies。
4. 节点集合：所有节点、地区节点、新增节点。
5. 自定义成员：只能包含新增节点、已知代理组和内置策略目标。

### 7.4 自定义代理组的模板化

用户新增代理组时：

- 如果成员来自标准配置，可完整记录。
- 如果成员包含新增节点，可记录。
- 如果成员包含已知代理组，可记录。
- 如果成员包含内置策略目标，可记录。
- 如果成员包含外部订阅原生节点，则不能作为模板稳定记录。

生成模板时要说明：

```text
代理组 “AI” 中的原生节点 “HK-01” 无法写入通用模板。
将只保留新增节点、自定义代理组、地区集合和内置策略目标。
```

最坏情况下，系统可以只记录“创建了这个代理组”，但代理组成员为空，并提醒用户补全模板。

### 7.5 顺序记录

如果用户把 ProxyParser 新增节点放在代理组顶部，需要特殊记录顺序。

规则：

- 新增节点置顶：记录为 template operation。
- 新增节点放在中间：可简化为放底部，保存前提示。
- 新增节点放底部：记录为 append。
- 原生节点的精确顺序不进入通用模板。

## 8. 规则模块设计

### 8.1 基本模型

规则不是“为规则源服务”，而是“为代理组/内置策略目标服务”。

推荐交互：

```text
目标：AI
  - 导入 OpenAI 规则源快照
  - 导入 Anthropic 规则源快照
  - 手动添加 DOMAIN-SUFFIX,example.ai

目标：Streaming
  - 导入 Netflix 规则源快照
  - 导入 Disney 规则源快照

目标：DIRECT
  - 导入 CN Domain
  - 导入 CN CIDR
  - 导入 Private

目标：REJECT
  - 导入 Reject Ads
```

最终生成规则链时，再按用户设置的顺序输出。

### 8.2 规则源导入后的绑定关系

导入规则源时，系统应 fetch 规则内容并生成规则快照。

Recipe 中记录：

- 来源规则源 ID / URL。
- 导入时间。
- 内容 hash。
- 导入后的规则条目。
- 目标代理组 / 内置策略目标。
- 插入位置。

此后规则与规则源不再强绑定。用户需要重新同步时，应该明确点击“重新导入规则源”，并确认 diff。

### 8.3 规则目标限制

规则目标只能是：

- 已知代理组。
- 内置策略目标：DIRECT、REJECT、PASS、COMPATIBLE。

规则不能指向不存在的代理组。

如果用户删除某个代理组，所有指向该组的规则必须进入待处理状态，不能静默生成非法 YAML。

### 8.4 规则类型

规则编辑器提供固定匹配类型，例如：

```text
DOMAIN
DOMAIN-SUFFIX
DOMAIN-KEYWORD
IP-CIDR
IP-CIDR6
GEOIP
GEOSITE
PROCESS-NAME
RULE-SET
MATCH
```

用户粘贴多条规则时，系统解析为结构化规则。

### 8.5 粘贴规则与规范化确认

用户粘贴规则后，系统会做：

- 解析。
- 校验目标。
- 去重。
- 排序建议。
- 修正常见空格、大小写、重复逗号。

如果保存结果与用户输入不完全一致，必须弹出确认：

```text
你粘贴了 42 条规则。
系统将：
- 移除 3 条重复规则。
- 将 2 条目标不存在的规则标记为待处理。
- 修正 5 条规则的空格。
- 把 MATCH 保持在最后。

确认后保存规范化结果。
```

### 8.6 规则模板化

Full Override 模式下，所有代理组都是可记录对象。

规则可以进入模板的条件：

- 目标是新增代理组、模板生成代理组或内置策略目标。
- 规则不直接引用外部订阅原生节点。
- 规则源导入结果已经快照化。

如果规则涉及原生节点或源订阅专属对象，不进入通用模板，并在模板生成报告中列出。

## 9. 模板设计

### 9.1 模板只支持 Full Override

Patch 模式说明用户在现有订阅上做小修小补，天然和源订阅绑定，不作为模板共享主链路。

Full Override 才能生成通用模板。

### 9.2 模板的意义

模板的意义是与订阅脱钩：换一个外部订阅，只要还有节点，套上模板就可以用。

模板应该记录：

- ProxyParser 新增节点。
- 节点标签和抽象集合使用方式。
- 代理组创建命令。
- 代理组标准成员配置。
- 服务代理组与规则目标关系。
- 导入规则源后的规则快照。
- 前置规则、后置规则、MATCH 规则。
- 配置覆盖。

模板不应该记录：

- 外部订阅原生节点的具体名称。
- 外部订阅 URL。
- 源订阅专属 proxy-provider。
- 源订阅专属 rule-provider。
- 源订阅专属规则链。

### 9.3 新增节点进入模板

用户在 ProxyParser 中新增的自定义节点可以进入模板。

例如：

- 新增 VPS 节点。
- 放入 Proxies 总组。
- 放入对应国家/地区组。
- 作为 AI 代理组的默认选择。

这些都应记录为模板操作。

### 9.4 原生节点的处理

原生节点来自外部订阅，不能被通用模板精确记录。

模板只能通过抽象方式引用原生节点：

- 所有启用节点。
- 某个地区标签的节点。
- 某个协议类型的节点。
- 系统计算出的地区代理组。

如果用户在 Full Override 中手动把某个原生节点放进自定义代理组，模板生成时应提示该操作无法进入通用模板。

### 9.5 模板生成报告

保存模板前必须显示报告：

```text
可记录：
- 1 个新增节点：Home VPS
- 8 个代理组创建命令
- 6 个规则目标配置
- DNS/TUN/Sniffer 配置

不可记录：
- 代理组 AI 中手动引用了原生节点 HK-01
- 规则 DOMAIN-SUFFIX,internal.test 指向了已删除代理组 OldProxy

系统将：
- 保留 AI 代理组，但移除无法模板化的 HK-01 成员
- 标记 OldProxy 规则为无效，不写入模板
```

## 10. 访问与 Key

### 10.1 扩展订阅详情内的访问与共享

扩展订阅详情展示：

- 复制长期订阅链接。
- 创建短期链接。
- 分享给指定用户。
- 非公开链接。
- 公开访问。
- 拉取日志。

### 10.2 设置内的长期 Key

设置中管理账号长期 Key：

- 当前长期 Key 状态。
- 最近使用时间。
- 重置长期 Key。
- Key 轮换历史。
- 风险提示。

扩展订阅详情复制长期链接时使用账号长期 Key。

## 11. UI 组件与交互规范

### 11.1 组件规范

前端实现时应使用统一 UI 组件系统，例如项目现有 Radix 风格组件体系，至少覆盖：

- Select。
- Dialog。
- Tabs。
- Popover。
- Tooltip。
- Toast。
- Badge。
- Table。
- Command / Combobox。

不要直接使用浏览器原生 Select 作为最终 UI，因为它在不同系统下样式不可控，也无法稳定展示选项说明。

### 11.2 Select 选项说明

构建模式、共享模式、规则目标、代理组成员配置等复杂选项，都需要支持标题 + 描述。

例如共享模式：

```text
不共享
仅自己可见，不允许 fork 或 subscribe。

允许 fork
别人可以复制脱敏 Recipe，但不能获得真实节点或 Key。

允许 subscribe
被授权用户可以拉取这个扩展订阅。
```

### 11.3 用户确认机制

只要系统保存结果与用户输入不完全等价，就必须确认。

典型场景：

- 粘贴规则后去重。
- 规则格式规范化。
- 节点重命名导致引用更新。
- 删除节点导致代理组成员移除。
- 删除代理组导致规则目标失效。
- 把自定义代理组模板化时移除原生节点。
- 多来源合并时丢弃源规则和源代理组。

## 12. 原型覆盖范围

更新后的原型覆盖：

- 工作台：真实产品标题、产品心智卡片、异常和常用订阅。
- 外部订阅：添加按钮、详情卡片、基于外部订阅创建扩展订阅、详情 Tab。
- 扩展订阅：新增按钮、订阅详情、复制长期链接、编辑构建逻辑、访问与共享。
- 构建器：非导航入口，8 步流程，包含多来源强制 Full Override、节点不默认清洗、代理组生成、规则目标化、确认机制、模板报告。
- 规则源：导入、预览、规则快照化说明。
- 模板：我的模板和模板共享二级结构，Full Override 模板化规则、不可记录项报告。
- 设置：长期 Key 管理。

## 13. 后续待讨论问题

1. 是否需要在模板中保存用户新增节点的完整敏感字段，还是只保存脱敏结构并要求应用模板时补全？
2. 多来源合并时，节点重名如何处理：自动加来源前缀、要求用户确认、还是用稳定 ID 隐藏差异？
3. 规则源快照化后，是否要提供“检查源规则更新并对比导入”的半自动流程？
4. 原生节点不能模板化时，是否允许用户把它转换为 ProxyParser 自定义节点？
5. 代理组标准成员配置是否需要支持用户自定义预设并进入模板？
6. 内置策略目标是否只保留 DIRECT / REJECT / PASS / COMPATIBLE，还是根据 Mihomo 能力扩展更多目标？
7. 规则顺序的默认策略如何定义：按目标分组、按规则包顺序、还是按用户手动顺序？
