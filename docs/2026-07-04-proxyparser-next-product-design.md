## 0. 这份文档是什么

v0.2 回答的问题是"交互应该长什么样"。这份文档先回退一步，回答"这个产品到底在解决什么问题"，再从这个答案推导出 Next 版本的对象模型、核心机制、信息架构和路线图。

结论先行——Next 版本的一句话定义：

> **ProxyParser 是你的订阅配置的家。机场订阅是原料，ProxyParser 里存放的是你确认过的、带版本的、永远可回滚的成品配置；客户端拉到的每一个字节都是你见过并同意的。**

这句话里的每个词都对应一个设计决策，后文展开。

## 1. 产品的本质：它到底在干什么

### 1.1 用户的真实处境

一个 Clash/Mihomo 用户的完整生命周期是这样的：

1. 买了一个或几个机场订阅。
2. 机场的原始配置不合心意：分组混乱、规则过时、没有 AI/流媒体分流、夹带广告组。
3. 想要自己的配置：自己的分组、自己的规则、自己的 DNS，可能还想混入自己的 VPS 节点。
4. 机场节点会变（增删、改名、换凭据），自己的配置必须自动跟上。
5. 手上有一堆设备（电脑、手机、路由器），都想订阅同一个稳定链接。
6. 机场偶尔抽风，不希望自己的配置跟着挂。
7. 换机场时，不想把上面所有工作重做一遍。

### 1.2 现有工具为什么都不够好

- **手改 YAML**：全能但每次上游更新都要重做，且没有校验，改错一个引用整个配置报废。
- **客户端 Merge/Script（Clash Verge Rev 等）**：绑定单设备，多设备不同步，需要会写 JS/YAML。
- **subconverter**：无状态转换器，ini 远程配置晦涩难学，没有账号、没有持久化，公共实例还有隐私风险。
- **Sub-Store**：最接近的竞品，但以脚本为中心，是给极客用的瑞士军刀，不是给普通用户的产品。

### 1.3 ProxyParser 的差异化价值

四件事，别人都没有同时做到：

1. **托管与兜底**：上游挂了，你的链接照常工作（快照回退）。
2. **可视化且保证正确**：不懂 YAML 也能重组配置，且系统保证引用永不悬空、产出永远合法。
3. **逻辑与原料分离**：你的组装逻辑（模板）独立于任何一个机场，换订阅即套用。
4. **确定与可控**：任何变化——你改的、上游改的、规则源改的——都看得见、可确认、可回滚。

前两点 V1 已经有雏形；后两点是 Next 版本要做透的。**"运行稳定"不是运维指标，它本身就是这个产品的核心功能。**

### 1.4 目标用户与非目标用户

- 核心用户：有 1~3 个机场订阅、多设备、对配置有想法但不想天天手工维护的 Clash/Mihomo 用户；愿意自部署或使用朋友部署的实例。
- 次级用户：帮家人朋友管理订阅的"家庭管理员"（共享能力为其服务）。
- 非目标（Next 阶段）：需要 sing-box/Surge 多格式输出的用户；需要节点测速选优的用户；大规模公开 SaaS 运营。

## 2. Next 版本的四个核心主张

这是整个设计的骨架，所有页面和功能都从这四条推导。

### 主张一：拉取的永远是"已发布版本"，发布才是产品的核心动词

现状问题：客户端拉取时系统"顺手"刷新上游并重新渲染。这意味着拉取可能慢、可能失败、可能返回用户从没见过的内容。这和"稳定托管"的承诺直接冲突。

Next 的模型借鉴部署平台（Vercel/Terraform）：

```text
编辑（草稿） → 预览 diff → 发布（生成不可变版本） → 客户端拉取已发布版本
```

- 每个订阅有一条**版本历史**。发布产生不可变的渲染快照，记录触发原因（手动 / 上游变化 / 规则源更新）、输入摘要和与上一版的 diff 概要。
- **拉取端点只读已发布版本**：毫秒级响应、可缓存、内容 100% 确定。拉取绝不触发同步渲染；上游同步全部走后台任务。
- **回滚**即"把历史版本重新发布为新版本"，一次点击。
- 上游变化时按订阅级策略处理（见 4.4）：默认自动发版（节点会换凭据，不自动跟进=坏掉），但每次自动发版都在版本历史里留下可读的变化摘要；谨慎用户可切换为"通知我确认后发布"。

这一条把"运行稳定"从口号变成机制。

### 主张二：构建配置是声明式的"期望状态"，不是操作日志

现状问题：草稿保存的是操作序列（add/patch/replace/remove，按名字引用目标）。操作日志有先天缺陷：顺序敏感、难以回放解释、中途修改历史等于重写宏、用户视角完全无法理解"我现在的配置到底是什么"。

v0.2 已经朝这个方向走了半步（"保存命令而不是一次性结果"），Next 走完整一步：**Recipe 不是日志，是一份声明式的构建配置文档（BuildConfig）**，渲染 = 用它对当前上游快照求值。

BuildConfig 的形状（示意）：

```yaml
mode: rebuild            # rebuild(完整重组) | patch(保留源配置)
sources: [src_abc, src_def]

nodes:
  transforms:            # 持续生效的转换管道，自动适用于未来新节点
    - strip-emoji
    - strip-multiplier
    - regex-replace: { from: "香港", to: "HK" }
  overrides:             # 针对单个稳定 ID 的钉住操作
    - id: n_9f2c
      rename: "HK-01"
    - id: n_71aa
      disabled: true
  custom:                # 用户自建节点（自有 VPS 等）
    - id: cn_home
      name: "Home VPS"
      secretRef: sec_01  # 敏感字段独立加密存储，见 6.1

groups:
  generators:            # 生成器：每次渲染重新求值，天然吸收上游节点增删
    - region-groups: { style: url-test, unclassified: Others }
    - auto-group: { name: Auto, members: all-enabled-nodes }
  custom:
    - name: AI
      type: select
      members:
        - ref: cn_home           # 自建节点：稳定 ID
        - group: Proxies         # 已知代理组
        - selector: { region: US }  # 抽象集合：可进模板
        - builtin: DIRECT        # 内置策略目标

rules:
  targets:               # 面向目标组织，不面向规则文件组织
    AI:
      - snapshot: { ref: rs_openai@sha256:ab12…, emit: provider }
      - manual: [ "DOMAIN-SUFFIX,example.ai" ]
    DIRECT:
      - snapshot: { ref: rs_cn_domain@sha256:cd34…, emit: provider }
  order: [ prelude, AI, Streaming, Ads, CN, DIRECT ]   # 块级排序
  final: MATCH,Proxies

config:
  dns: { … }             # 结构化字段
  rawPatch: |            # 逃生舱：raw YAML patch，发布前校验
    …
```

为什么声明式赢：

- **幂等可重放**：换一个上游快照直接重新求值，不存在"操作历史在新数据上重放失败"这种事。
- **用户可理解**：BuildConfig 就是"我的配置现在的定义"，可以整体查看、diff、导出。
- **模板 = 同一份文档去掉源绑定引用**。模板提炼从"分析操作流"退化为"过滤文档字段"，可靠十倍。
- **批量操作有了正确语义**：批量"去 emoji"保存为持续生效的 transform（未来新节点自动适用）；单点改名保存为 ID 级 override。两者都声明式，且用户能分别看到和删除。

UI 上不需要向用户展示"操作流"这个词。用户在各模块里编辑，系统落到 BuildConfig；高级用户可以看/导出整份 BuildConfig（JSON/YAML），这本身就是一种透明度。

### 主张三：联动对象模型——引用永不悬空（继承 v0.2 并落实到存储层）

v0.2 第 6~8 章的联动模型是对的，Next 全盘继承并强调它必须落到存储层，而不只是 UI 约束：

- 节点、代理组、规则快照、自建节点全部有**稳定 ID**；一切引用基于 ID，名字只是展示属性（当前代码按 `targetName` 引用，必须迁移）。
- 代理组成员只能是：已知节点 ID / 已知代理组 / 抽象选择器 / 内置策略目标（DIRECT、REJECT、REJECT-DROP、PASS、COMPATIBLE）。
- 规则目标只能是：已知代理组 / 内置策略目标。
- 删除或禁用任何被引用对象，引用方进入**"待处理问题"**清单（见 4.4），不阻塞编辑，但阻塞发布或在自动发版时降级为"保留上一版 + 亮黄灯"。系统永不静默生成非法 YAML，也永不静默"帮你修好"。

### 主张四：解释一切，不悄悄改任何东西（继承 v0.2）

v0.2 第 11.3 节的确认机制全盘继承：凡保存结果与用户输入不完全等价（规则去重、格式规范化、引用联动修改、模板脱敏丢弃），必须弹出明细确认。Next 把它推广为统一机制：

- 所有确认都以 **diff 的形式**呈现（"系统将做这 4 件事"），而不是抽象警告。
- 展示层的**推断不算修改**：节点列表可以显示系统推断的地区徽章（用于地区组生成预览），只要不写回数据，就不违反"不默认清洗"原则。推断结果用户可一键采纳为标签，也可无视。

## 3. 对象模型与术语

### 3.1 五个一等对象

```text
订阅源 (Source)        上游原料。URL、同步状态、快照序列。只读。
订阅 (Subscription)    产品核心。= 订阅源(1..n) + BuildConfig + 发布设置 + 版本历史 + 访问控制。
规则库 (Ruleset)       规则素材目录 + 不可变内容快照（按 hash 寻址）。
模板 (Template)        源无关的 BuildConfig，可版本化、可分享、可应用。
版本 (Release)         订阅的一次不可变发布产物：渲染结果 + 输入指纹 + diff 摘要。
```

### 3.2 术语更名

概念数量是新用户的第一道门槛。"外部订阅 vs 扩展订阅"要求用户先理解产品架构才能理解导航。Next 统一为：

| 旧术语 | Next 术语 | 理由 |
|---|---|---|
| 外部订阅 / upstream_source | **订阅源** | "源"字直接表达"原料"语义 |
| 扩展订阅 / managed_subscription | **订阅** | 这是产品主角，用最短的词；用户心智里"我的订阅"就是它 |
| 规则源 / ruleset_catalog | **规则库** | 避免与"订阅源"双重"源"字混淆 |
| Recipe / 操作流 / 草稿 | **构建配置**（BuildConfig） | 对用户基本不可见，仅高级视图出现 |
| 渲染快照 | **版本**（Release） | 借部署平台心智 |

数据库表名不必跟着改，做映射即可。

### 3.3 构建模式：保留两种，重新命名

- **重组模式（rebuild）**：只取源的节点，组、规则、配置全部自建。可模板化。多源合并强制此模式且只合并节点（继承 v0.2 第 5.3 节）。
- **微调模式（patch）**：保留源配置整体，做小修。源绑定、不可模板化，产品明确告知此限制。价值在于"机场配置本来不错，我只想加个自建节点+托管兜底"这类用户。

模式在创建时通过"起点选择"隐式确定（见 5.3），不作为一个要用户先学习的抽象概念。

## 4. 关键机制设计（与 v0.2 的分歧与推进）

### 4.1 规则快照 + 托管 rule-provider：两全方案

v0.2 第 8.2 节说规则源导入后快照化、最终配置面向目标组织规则——方向对（用户确认过的规则不能被远端悄悄改变），但如果理解为"把规则内联进 YAML"，会带来新问题：CN 域名表几万条，内联导致配置巨大、客户端解析慢，还丢掉了 Mihomo rule-provider 的原生能力。

当前实现则是另一个极端：rule-provider 指向服务的**可变**内容端点 + `interval: 86400`，远端规则更新会静默流入用户配置——恰是 v0.2 要消灭的。

Next 的方案两全：**快照钉版本，输出仍走 provider**。

```text
导入规则源 → fetch → 生成内容寻址快照 (sha256) → BuildConfig 引用 snapshot@hash
渲染时按 emit 策略输出：
  emit: provider（默认，大规则集）
    rule-providers.<slug>:
      type: http
      url: https://<host>/rs/<hash>.yaml     # 不可变端点，永远返回同一内容
      format: yaml                            # 后续可升级 mrs
    rules: RULE-SET,<slug>,<目标组>
  emit: inline（小规则集 / 手动粘贴规则 / 私有规则）
    直接内联为普通规则条目
```

- 不可变哈希端点 = 客户端侧也享受确定性；provider 不配置自动更新间隔，内容永不漂移。
- **更新是显式动作**：规则库页对每个已缓存规则源做后台定期抓取，源有新内容时打"有更新"徽章；用户点开看 diff（+120 条 / -3 条），确认"更新到新快照"后，所有引用该规则源的订阅进入"待发布变更"，走正常发布流程。半自动、有 diff、可批量——这直接回答 v0.2 遗留问题 3。
- 用户粘贴的私有规则默认 inline（避免私有内容出现在公开哈希端点上）。

### 4.2 上游变化的吸收：同步报告 + 发布策略 + 健康灯

上游订阅变化是这个产品最频繁的外部事件，Next 把它做成一等公民：

**同步报告**：每次源同步成功后，与上一快照做结构化 diff：

```text
订阅源「XX机场」 06-30 14:00 同步
+ 新增节点 3（US-04, US-05, SG-02）
- 移除节点 1（HK-03）
~ 凭据轮换 12
影响：订阅「日常」的地区组自动吸收；自定义组「AI」引用的 HK-03 已失效 → 待处理
```

**发布策略**（订阅级设置）：

- `自动`（默认）：上游变化 → 后台重渲染 → 校验通过则自动发布新版本，版本历史记录变化摘要；校验失败或产生待处理问题 → 保留上一版继续服务，亮黄灯。
- `确认`：只生成待发布草稿，通知用户看 diff 后手动发布。

**健康灯**（订阅级，工作台首屏的核心信息）：

```text
● 正常   最新版本服务中，上游新鲜
● 注意   上游同步失败/过期，正在服务 N 小时前的版本；或存在待处理问题
● 故障   无任何可用版本，或拉取端点异常
```

**待处理问题清单**：所有悬空引用、未分类节点、校验警告收敛到订阅详情的"问题"页签，每条问题给出一键修复建议（"从 AI 组移除 HK-03" / "把未分类节点归入 Others"），修复动作本身也走确认。

### 4.3 发布前校验：用 Mihomo 内核当裁判

自研校验器覆盖结构问题（引用存在性、名称唯一、MATCH 落点、provider behavior 匹配——继承 05-14 规格第 5 节清单），但"Mihomo 能不能加载"的最终裁判应该是 Mihomo 本身：

- 部署时可选捆绑 mihomo 二进制，发布流水线执行 `mihomo -t -f <rendered.yaml>` 作为最后一道门。
- 校验失败的配置**不可能**被发布，错误原文展示给用户。
- 没有二进制的部署环境自动降级为仅结构校验，并在实例健康页提示。

这一条花费极小，换来的是"从 ProxyParser 拉到的配置必然能被客户端加载"的硬承诺。

### 4.4 规则追踪器："这个域名会走哪"

用户编辑规则时真正的问题从来不是"我的规则列表长什么样"，而是"`netflix.com` 到底会命中哪条规则、走哪个组"。Next 在编辑器和订阅详情内置追踪器：

```text
输入: chat.openai.com
结果: 命中 RULE-SET geosite-openai (第 3 块, 规则 #142) → 目标组 AI
      AI 当前选择: Home VPS
```

对草稿和已发布版本都可用。实现上就是对渲染结果跑一遍规则匹配，成本低，价值极高——它同时是学习工具、调试工具和"改完规则验证有没有生效"的确认工具。

### 4.5 访问模型：Key 按订阅独立

现状是账号级长期 Key，一把钥匙开所有订阅——轮换一次，所有设备的所有订阅链接同时作废，用户会因为害怕而永不轮换。Next 改为：

- **每个订阅独立的长期 token**：`https://<host>/s/<subId>/<token>`。轮换只影响一个订阅。
- 短期分享链接（可设 TTL、可撤销）、指定用户授权，均在订阅详情的"访问"页签管理（继承 v0.2 第 10.1 节）。
- 设置页保留全账号 token 总览与批量轮换、拉取审计。
- 拉取响应带 `subscription-userinfo` 透传、`content-disposition` 文件名、`profile-update-interval` 提示头；详情页提供二维码和 `clash://install-config` 一键导入。

### 4.6 编辑器：从"向导"改为"工作台"

8 步向导对创建是引导，对编辑是刑罚——改一条规则要在线性步骤里穿行。Next 拆开两者：

- **创建 = 3 步向导**（见 5.3），目标是 3 分钟拿到链接。
- **编辑 = 工作台**：左侧模块导航（概览 / 节点 / 代理组 / 规则 / 配置 / 版本与访问），右侧常驻**诊断栏**（问题清单、YAML 预览、与已发布版本的 diff、规则追踪器）。非线性、随时保存草稿、随时预览、显式发布。

## 5. 信息架构与页面设计

### 5.1 主导航

```text
工作台        所有订阅的健康灯 + 最近事件（同步报告、发布、拉取异常）
订阅          我的订阅列表（产品主角）
订阅源        上游原料管理
规则库        规则源目录、缓存状态、更新徽章
模板          我的模板 / 模板广场
设置          账号、token 总览、实例健康、备份
```

与 v0.2 的差别：外部/扩展订阅不再作为"订阅"下的两个子项并列——它们地位不对等，订阅是主角，订阅源是原料，分开成两个顶级项反而更清晰。构建器不入导航（继承 v0.2）。

### 5.2 工作台

不是营销页，是状态页。回答三个问题：我的订阅都健康吗？最近发生了什么？有什么需要我处理？

- 订阅健康卡片（灯 + 最近发布时间 + 最近拉取时间）。
- 事件流：同步报告、自动发布记录、规则源更新徽章、失败告警。
- "待处理"聚合入口。

### 5.3 创建订阅：黄金路径 3 分钟

新用户的第一次成功必须又快又好：

```text
第 1 步  粘贴订阅 URL（或选已有订阅源）
         → 立即同步，展示：45 个节点 / 28 个源代理组 / 16 条源规则 / 流量与到期
第 2 步  选择起点（隐式决定构建模式）：
         ① 推荐方案（默认高亮）— 官方维护的起手模板：Proxies/Auto/地区组 +
            AI/流媒体/广告/CN 分流 + 合理 DNS。选它 = rebuild 模式。
         ② 套用我的模板 / 广场模板 = rebuild 模式。
         ③ 保留机场原版配置，仅做小修 = patch 模式。
         ④ 空白自建 = rebuild 模式。
第 3 步  命名 → 预览摘要 → 发布 → 拿到链接 + 二维码 + 客户端导入指引
```

官方"推荐方案"是产品级资产，随产品版本维护更新，也是模板系统的示范样本。精修在创建之后进工作台做——向导不承载编辑深度。

### 5.4 订阅详情（工作台形态）

```text
┌ 概览    健康灯、当前版本、来源、统计、快捷操作（复制链接/立即同步/编辑）
├ 节点    见 6.1
├ 代理组  见 6.2
├ 规则    见 6.3
├ 配置    结构化表单（DNS/TUN/Sniffer/端口/mode）+ raw patch 逃生舱
├ 版本    版本历史、每版 diff、回滚、待发布草稿对比
├ 访问    长期 token、短期链接、授权用户、拉取日志、二维码
└ 问题    待处理清单 + 一键修复建议
（右侧常驻诊断栏：YAML 预览 / 与已发布 diff / 规则追踪器）
```

### 5.5 UI 规范

继承 v0.2 第 11 章全文：统一 Radix 风格组件体系；Select 选项带标题+描述；不用浏览器原生下拉；所有异步操作有状态反馈。补充两条：

- diff 是一等 UI 组件：版本 diff、规则源更新 diff、确认弹窗，统一视觉语言。
- 高密度控制台审美（继承 05-14 规格第 9 节），信息密度优先于装饰。

## 6. 模块细则

（与 v0.2 一致的部分不重复展开，只记录差异与补充。）

### 6.1 节点

- 默认零修改展示（继承 v0.2 第 6.1 节全部"不默认"清单）。
- 列表附**推断徽章**：地区、协议等展示层推断，不写数据；一键"采纳为标签"。
- 批量清洗动作保存为**持续 transform**（新节点自动适用），单点改名保存为 **ID 级 override**；两类都在"节点规则"面板可见、可删。
- 自建节点的敏感字段（密码/UUID/私钥）**单独加密存储**（secretRef），BuildConfig 与模板只持有引用。模板导出时 secretRef 变为占位符，应用模板时要求补全——回答 v0.2 遗留问题 1。
- 原生节点可"**转为自建节点**"（拷贝当前凭据，脱离源生命周期），并警告机场轮换凭据后需自行维护——回答遗留问题 4。
- 多源重名：内部靠稳定 ID 无歧义；渲染输出名冲突时自动加源前缀，并在发布确认中列出——回答遗留问题 2。

### 6.2 代理组

- 生成器（地区组 / Auto / 推荐服务组）是 BuildConfig 的持久声明，每次渲染重新求值——这是 v0.2 "保存命令"思想的完成形态。
- 成员约束与标准成员配置继承 v0.2 第 7.3 节；**用户可把常用成员组合保存为自定义预设，预设可进模板**——回答遗留问题 5。
- 成员顺序：静态成员（自建节点、组、内置目标）精确排序；抽象选择器作为块整体参与排序；原生节点单点引用不进模板（继承 v0.2 第 7.4/7.5 节）。

### 6.3 规则

- 面向目标组织（继承 v0.2 第 8.1 节），每个目标一份"路由清单"。
- **全局顺序视图**：前置块 → 各目标块（可拖动块级排序）→ MATCH 兜底钉底。块内顺序 = 快照序 + 手动插入位——回答遗留问题 7。
- 粘贴规则的解析/去重/规范化确认，继承 v0.2 第 8.5 节原文。
- 规则快照与 emit 策略见 4.1；规则追踪器见 4.4。
- 内置策略目标：DIRECT / REJECT / REJECT-DROP / PASS / COMPATIBLE，按目标方言版本能力表驱动，未来扩展不改架构——回答遗留问题 6。

### 6.4 模板

- 仅 rebuild 模式可模板化（继承 v0.2 第 9.1 节）。
- 模板 = BuildConfig 的源无关子集，提炼即字段过滤 + 报告（继承 v0.2 第 9.5 节的可记录/不可记录报告，实现上大幅简化）。
- 应用模板 = 3 步：选订阅源 → 补全占位符（自建节点凭据、未分类节点归置）→ 预览并创建。
- 模板版本化保留；分享以"链接 + 导入"为主，广场只保留官方起手方案与公开列表，社交功能（评分、评论、关注）明确不做——单人体验没做到极致之前，生态是空中楼阁。

### 6.5 设置与实例运维

自部署体验是产品的一部分，不是文档的一部分：

- 单容器 + SQLite + 零配置启动；首次启动引导创建管理员。
- 设置页内置**备份/恢复**：一键导出加密备份（含 secrets），一键恢复。
- 实例健康页：后台任务状态、mihomo 校验器可用性、磁盘、快照 GC 情况。
- 隐私立场写进产品：节点数据不出你的服务器，无遥测。

## 7. 稳定性工程要求

这些是验收标准，不是愿景：

1. **确定性渲染**：相同（上游快照 + BuildConfig）→ 字节级相同的 YAML。所有集合输出有稳定排序。用 golden 测试锁住。
2. **拉取 SLO**：拉取端点只读已发布 Release，目标 p99 < 100ms，绝无同步上游请求。
3. **降级链清晰**：最新版本 → （不存在时）明确错误；后台渲染失败绝不影响服务中的版本。
4. **发布门禁**：结构校验 + mihomo -t（可用时）双重通过才能发布。
5. **迁移安全**：现有 managed_subscriptions 的操作流由一次性转换器折算为 BuildConfig；按名引用解析为 ID，解析失败的进该订阅的"问题"清单而不是静默丢弃；旧拉取 URL 保持兼容或 301。
6. **测试基线**：渲染 golden 测试、发布流水线集成测试、拉取降级测试、模板提炼/应用往返测试（提炼→应用→再提炼应收敛）。

## 8. 明确不做（Next 版本非目标）

- sing-box / Surge / Loon 多格式输出。内部表示不排斥未来支持，但 Next 只出 Mihomo YAML。
- 节点测速、可用性探测、自动选优——那是客户端的工作（url-test）。
- 模板市场的社交化运营。
- 多租户 SaaS 计费与组织权限。
- 移动端 App。订阅链接 + 二维码已覆盖移动场景。

## 9. 路线图

按依赖排序，每个里程碑独立可验收：

**M1 — 模型地基（最大的一次手术）**
稳定 ID 落库；BuildConfig 声明式模型 + 旧操作流转换器；联动引用与"问题"清单；确定性渲染 + golden 测试。
验收：旧数据无损迁移，渲染结果与迁移前 diff 可解释。

**M2 — 发布流水线**
Release 版本化；不可变拉取端点 + 按订阅 token；后台同步调度与同步报告；发布策略（自动/确认）；健康灯；mihomo -t 门禁。
验收：拉取 p99 达标；上游变化产生带 diff 摘要的自动版本；回滚一键可用。

**M3 — 规则体系**
规则快照内容寻址存储 + 不可变 /rs/<hash> 端点；emit 策略；规则库更新徽章与 diff 更新流；目标化规则编辑器 + 全局顺序视图；规则追踪器。

**M4 — 工作台编辑器与黄金路径**
订阅详情工作台（含右侧诊断栏）；3 步创建向导；官方推荐方案模板；节点 transform/override 面板；确认弹窗体系统一为 diff 形态。

**M5 — 模板与分享收敛 + 运维打磨**
模板提炼/应用新链路；占位符补全流程；分享简化为链接+导入；备份/恢复 UI；实例健康页；前端代码分割（清掉 500kB warning）；文档与部署指引。

## 10. 成功标准

Next 版本完成的定义：

1. 新用户从粘贴 URL 到客户端成功导入 ≤ 3 分钟，全程无需理解"模板/构建模式/Recipe"任何一个词。
2. 任意上游节点增删/改名/换凭据后，用户的地区组与规则在下一次自动发布中正确吸收，且版本历史能讲清楚发生了什么。
3. 上游连续宕机 72 小时，订阅链接仍以毫秒级返回最后已发布版本，健康灯如实变黄。
4. 用户做的任何编辑，在发布前都能看到与线上版本的完整 diff；发布后可一键回滚。
5. 从 ProxyParser 拉取的配置在 Mihomo 上加载失败率为 0（有校验门禁兜底）。
6. 换一个机场：新建订阅源 → 套用自己提炼的模板 → 补全占位符 → 发布，10 分钟内完成，规则与分组零重做。
